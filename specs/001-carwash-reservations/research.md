# Research: Carwash Reservations

**Feature**: `001-carwash-reservations` | **Date**: 2026-10-20 | **Plan**: [plan.md](./plan.md)

Each entry records a decision, why it was made, and what was rejected. The stack itself (Go,
gqlgen, PostgreSQL, sqlc + pgx, golang-migrate, testcontainers, slog, distroless image) is fixed
by the constitution and is not re-litigated here.

## R1. Toolchain versions

- **Decision**: Go 1.27 (`go 1.27` in `go.mod`); PostgreSQL 19 (`postgres:19` image in compose and
  testcontainers).
- **Rationale**: Constitution I and III require the latest stable releases. Pin exact patch tags
  only in the Dockerfile/compose; testcontainers uses the same major as compose.
- **Alternatives considered**: Pinning the previous release for stability, rejected by the
  constitution. If a release is unavailable on a developer machine at implementation time,
  update the major in one place (compose + test helper constant) and record it in the PR.

## R2. Preventing overlapping reservations (FR-009)

- **Decision**: A PostgreSQL exclusion constraint on the reservation's time slot, restricted to
  active rows:
  `EXCLUDE USING gist (tstzrange(starts_at, ends_at, '[)') WITH &&) WHERE (cancelled_at IS NULL)`.
  `ends_at` is stored on the row (computed by the service from the service type's duration when
  the row is written). An exclusion violation (SQLSTATE `23P01`) is translated by the store into
  `ErrSlotConflict`.
- **Rationale**: The database enforces the invariant atomically, so simultaneous requests cannot
  both succeed (spec edge case) without application-level locks. The half-open range `[)` makes
  back-to-back slots legal. The partial `WHERE` means cancelled reservations never block. GiST on
  a single range column needs no extension (no `btree_gist`).
- **Alternatives considered**:
  - `SELECT ... overlapping` then `INSERT` in the application: racy unless done under
    `SERIALIZABLE` or an advisory lock; more code, weaker guarantee.
  - Unique constraint on `starts_at`: sufficient today (hourly grid, 60-minute carwash) but
    breaks as soon as a service type lasts longer than one grid hour.
  - Generated column for `ends_at`: cannot reference the `service_types` table.

## R3. Hourly start-time grid (FR-003)

- **Decision**: Validate in the service (`t.Truncate(time.Hour).Equal(t)` on the UTC
  instant, which also forces zero seconds/nanoseconds) and back it with a table check constraint
  `CHECK (extract(epoch FROM starts_at)::numeric % 3600 = 0)`.
- **Rationale**: The service produces a per-field validation error (`NOT_ON_GRID`); the check
  constraint guarantees no other writer can violate the invariant (Constitution III).
- **Alternatives considered**: Validation only in Go (weaker invariant), only in SQL (no per-field
  client error).

## R4. Identifiers

- **Decision**: UUIDv7 generated by PostgreSQL (`DEFAULT uuidv7()`, built in since PostgreSQL 18),
  exposed in GraphQL as `ID` in canonical text form.
- **Rationale**: Stable, unguessable enough for a trusted-network API, time-ordered (good index
  locality), and needs no Go UUID dependency: sqlc maps `uuid` to `pgtype.UUID`, formatted with
  its `String()` method and parsed with `Scan` at the boundary.
- **Alternatives considered**: `bigserial` (leaks volume, easy to enumerate); `github.com/google/uuid`
  (extra dependency with no benefit, Constitution I).

## R5. Service types (FR-004, SC-005)

- **Decision**: A `service_types` table (`code` PK, `display_name`, `duration_minutes`,
  `offered`) seeded with `carwash / Carwash / 60 / true` in a migration. GraphQL input takes the
  service type as a `String!` code; output exposes a `ServiceType` object. Reservation queries
  join `service_types`, so the object is loaded in the same query.
- **Rationale**: Adding a service type is a data change (migration or operator SQL) with no schema
  change, satisfying SC-005. A GraphQL enum would require a schema change per new type. Joining
  instead of a separate resolver removes any N+1 risk without needing a DataLoader
  (Constitution II's DataLoader rule applies to resolvers that load related entities; there are
  none here).
- **Alternatives considered**: GraphQL enum (schema change per type); hard-coded Go map (violates
  "runtime-mutable configuration lives in PostgreSQL").

## R6. Soft delete and status (FR-007)

- **Decision**: `cancelled_at timestamptz NULL`; status is derived (`ACTIVE` when null,
  `CANCELLED` otherwise) rather than stored separately.
- **Rationale**: One column cannot disagree with itself; the exclusion constraint and the listing
  index both use `cancelled_at IS NULL`.
- **Alternatives considered**: a `status` column plus `cancelled_at` (two sources of truth needing
  a check constraint to keep them consistent).

## R7. Bounded listing without pagination (FR-005, Constitution II)

- **Decision**: `reservations(from, to): [Reservation!]!` returns every active reservation whose
  start is in `[from, to)`, ordered by `(starts_at, id)`, with no paging arguments. The service
  caps a listing at `MaxListResults = 1000`: the store query uses `LIMIT 1001`, and if 1001 rows
  come back the service returns `ErrTooManyResults`, which the resolver reports as a GraphQL error
  with `extensions.code = "TOO_MANY_RESULTS"` (no partial data). The partial index
  `(starts_at, id) WHERE cancelled_at IS NULL` serves the query.
- **Rationale**: the frontend lists short periods (a day or a week: at most 168 active hourly
  slots per week), so one response always fits and a flat list is the simplest contract.
  Fetching one row beyond the cap detects overflow in the same query, without a separate
  `COUNT(*)`. Failing instead of truncating means a client never mistakes a partial list for the
  full one. `id` keeps the order deterministic.
- **Alternatives considered**: Relay cursor connection (previous design; dropped as needless
  complexity for these period sizes, constitution v2.0.0); silently truncating at 1000 (a
  client can't tell the list is incomplete); `COUNT(*)` before the select (an extra query, and the
  count can change between the two statements).

## R8. Error model (FR-011, Constitution II)

- **Decision**:
  - Mutations return payloads with `reservation` and `errors: [UserError!]!`. `UserError` is an
    interface implemented by `ValidationError` (`field`, `code`), `NotFoundError` and
    `SlotConflictError`.
  - Queries (`reservation`, `reservations`) report client errors as GraphQL errors with a stable
    `extensions.code`: `NOT_FOUND`, `BAD_USER_INPUT` (plus `extensions.field`),
    `TOO_MANY_RESULTS` (listing matched more than 1000 reservations).
  - Any other error is logged with the request ID and returned to the client as
    `INTERNAL_SERVER_ERROR` with a generic message (gqlgen error presenter + recover func).
- **Rationale**: Mutation failures are part of normal use and benefit from typed, multi-field
  results; query failures are rare and simple, so `extensions.code` keeps the query shape clean.
  Both styles are explicitly allowed by the constitution.
- **Alternatives considered**: `extensions.code` for everything (loses per-field typing for
  forms); result unions on queries (heavier client code for no gain).

## R9. Validation rules (FR-003)

- **Decision** (all applied after trimming whitespace):
  - name: 1–200 characters (counted in Unicode code points).
  - email: ≤254 characters (counted in Unicode code points, matching PostgreSQL `length()`), accepted by `net/mail.ParseAddress` and equal to the parsed
    `Address` (rejects display-name forms like `Bob <b@x.hu>`), domain contains a dot. Stored as
    trimmed input.
  - phone: matches `^\+?[0-9 ()./-]+$` and contains 7–15 digits.
  - startsAt: strictly after "now" (injected clock), on the hourly grid.
  - serviceType: an existing code with `offered = true` (on update, only checked when it changes;
    a retired type the reservation already has is kept).
  - Update of a reservation whose start has already passed: only name, email and phone may change;
    supplying a `startsAt` or `serviceType` different from the current value returns
    `NOT_ALLOWED` for that field; a supplied value equal to the current one counts as unchanged.
  - All failures are collected (not first-error-only) so every invalid field is reported.
- **Rationale**: standard library only (Constitution I); collecting all errors satisfies
  acceptance scenarios 1.2 and 3.2.
- **Alternatives considered**: a validation library (unnecessary dependency).

## R10. Concurrency on update/delete

- **Decision**: Update and delete run in one transaction: `SELECT ... FOR UPDATE` the row, apply
  rules, `UPDATE`. Overlap is still enforced by the exclusion constraint. Concurrent edits of the
  same reservation are last-writer-wins (accepted: small business, single staff UI).
- **Rationale**: Row lock prevents a delete and an update interleaving (e.g. updating a row that
  was just cancelled). Optimistic versioning was not requested by the spec (YAGNI).
- **Alternatives considered**: version column with compare-and-swap (deferred until needed).

## R11. HTTP server, playground, limits

- **Decision**: `net/http` `ServeMux` with routes `POST/GET /graphql` (gqlgen
  `handler.New` + POST/GET transports), `GET /livez`, `GET /readyz`, and `GET /playground` only
  when `APP_ENV=development`. Introspection extension added only in development. Complexity limit
  via gqlgen `extension.FixedComplexityLimit(GRAPHQL_MAX_COMPLEXITY)`; depth limit via a small
  custom `graphql.HandlerExtension` (`OperationContextMutator`) that walks the operation's
  selection set (gqlgen has no built-in depth limit). Middleware: request ID, structured access
  log, panic recovery, CORS.
- **Rationale**: Only the user-requested standard server; no router dependency. Separate
  playground path keeps `/graphql` identical across environments.
- **Alternatives considered**: `handler.NewDefaultServer` (deprecated, enables introspection
  unconditionally); a third-party router or CORS package (unnecessary, Constitution I/VI).

## R12. Configuration

- **Decision**: Environment variables, parsed once in `main` into a `config.Config` struct (no
  dependency); missing/invalid values fail fast with a message listing every problem.

| Variable | Required | Default | Meaning |
|---|---|---|---|
| `DATABASE_URL` | yes | — | pgx connection string |
| `HTTP_ADDR` | no | `:8080` | listen address |
| `APP_ENV` | no | `production` | `development` or `production` |
| `CORS_ALLOWED_ORIGINS` | yes in production | — (dev: `*` allowed) | comma-separated origins; `*` rejected in production |
| `GRAPHQL_MAX_DEPTH` | no | `10` | query depth limit |
| `GRAPHQL_MAX_COMPLEXITY` | no | `200` | query complexity limit |
| `SHUTDOWN_TIMEOUT` | no | `15s` | graceful drain timeout |
| `LOG_LEVEL` | no | `info` | `debug`/`info`/`warn`/`error` |

- **Rationale**: 12-factor (Constitution IV), wildcard CORS banned outside dev (VI).

## R13. Migrations and startup

- **Decision**: Migrations live in `internal/store/migrations` as `NNNNNN_name.up.sql` /
  `.down.sql`, embedded with `embed.FS` and applied by golang-migrate (`iofs` source,
  `pgx/v5` database driver) in `main` before the HTTP listener starts. Readiness reports ready
  only after migrations succeeded and while `pool.Ping` succeeds.
- **Rationale**: Constitution III/IV; embedding keeps the image to a single binary.

## R14. Logging

- **Decision**: `slog.New(slog.NewJSONHandler(os.Stdout, ...))` created in `main` and injected.
  A middleware assigns a request ID (accepts incoming `X-Request-ID` if well-formed, otherwise
  generates one), stores it in the context, and a context-aware handler wrapper adds
  `request_id` to every record logged with that context. Customer email/phone are never logged.
- **Rationale**: JSON logs as requested; personal data stays out of logs (Constitution VI).

## R15. Testing strategy

- **Decision**:
  - Unit (table-driven, `-race`): validation rules, grid check, listing result cap, config
    parsing, depth limiter, error mapping. The service is tested against a hand-written fake that
    satisfies the store interface the service declares.
  - Integration (testcontainers, `postgres:19`): every sqlc query, exclusion constraint and
    concurrency (parallel creates for the same slot → exactly one success), grid check
    constraint, listing boundaries and row limit, migrations up → down → up.
  - API end-to-end: `httptest` server with real gqlgen handler + real store on testcontainers,
    covering every acceptance scenario in the spec.
  - One PostgreSQL container per package via `TestMain`; each test gets a fresh database created
    from a migrated template database for isolation and speed.
- **Rationale**: Constitution V; the fake service store complements but does not replace DB tests.

## R16. Container image and compose

- **Decision**: Multi-stage Dockerfile: `golang:1.27` build stage (`CGO_ENABLED=0`, `-trimpath`,
  `-ldflags="-s -w"`), final `gcr.io/distroless/static-debian13:nonroot`. `compose.yaml` runs
  `postgres:19` with named volume `pgdata` and a `pg_isready` healthcheck, and `bff` with
  `depends_on: condition: service_healthy`, `APP_ENV=development`. Distroless has no shell, so the
  BFF's container healthcheck is left to the orchestrator via `/readyz`.
- **Rationale**: Constitution IV and the user's named-volume requirement.
